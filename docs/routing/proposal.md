# Архитектурное предложение: Единая гибридная маршрутизация Jarvis без блокирующих keyword-гейтов

> **Статус**: Архитектурное предложение (RFC / Design Proposal)  
> **Контекст**: Базовый замер показал 50.7% Kind Accuracy, 58.6% ложных срабатываний на негативах и 40% пропусков High-Risk из-за блокирующих эвристик `intent == 'none'` и жестких regex.  
> **Ограничение**: Никаких новых надстроек и лишних сущностей — слияние и очистка существующего стека.

---

## 1. Концепция: Ключевое слово как Shortcut, а не Gate

Главный архитектурный дефект текущего решения — **инверсия роли ключевых слов**:
- *Как должно быть*: Ключевое слово — это бесплатный шорткат (0 мс) для мгновенного выполнения очевидных шаблонных команд («громче», «открой блокнот»).
- *Как сделано сейчас*: Ключевое слово — это блокирующий пропуск (Gate). Если пользователь перефразировал фразу живым языком («врубай телегу», «почём бакс»), запрос получает метку `intent = none` и при длине $\le 8$ слов **принудительно уходит в диалоговую модель**, лишаясь возможности вызвать даже встроенный семантический поиск инструментов.

### Принцип целевой архитектуры
1. **Несовпадение ключа — не повод для отказа**: Запрос не признается разговором только потому, что в нем нет слов из словаря 2024 года.
2. **Семантика по умолчанию**: Любая фраза, не попавшая в мгновенный шорткат, передается в векторный скоринг по паспортам возможностей (`CAPABILITIES`), который уже реализован в проекте.
3. **Разговор — это отдельный класс семантики, а не мусорная корзина**: Smalltalk и поддержка имеют свои четкие семантические центроиды («мне грустно», «как дела»), а не определяются по принципу «всё, что не подошло под regex».

## 2. Единый каскадный порядок маршрутизации

```
[Пользовательский ввод]
         │
         ▼
[0. Консервативный Risk Filter] (параллельно: выявление потенциально деструктивных корней и путей)
         │
         ▼
[1. Tier-0A: Exact Fast Shortcut] (0-1 мс, офлайн)
    ├── Точный проверенный глагол + имя приложения/системы И risk == LOW?
    │       ├── ДА  ──► Мгновенный Fast Path (open_app, volume, current_time)
    │       └── НЕТ ──► (Не блокируем! Передаем в Tier-0B)
         │
         ▼
[2. Tier-0B: Semantic Vector Retrieval] (5-15 мс, офлайн, all-MiniLM-L6-v2)
    ├── Косинусная близость по паспортам Capabilities (описания + примеры + теги)
    │       ├── Скор >= 0.75 ──► Уверенное действие / Fast Path / Fresh Data
    │       ├── Скор < 0.35  ──► Уверенный разговор / Вопрос (Conversational Tier)
    │       └── 0.35 .. 0.75 ──► СЕРАЯ ЗОНА (Tier-1)
         │
         ▼
[3. Tier-1: Ultra-Fast LLM Router] (80-180 мс, локальный Qwen 4B / DeepSeek FAST)
    ├── JSON-ответ одной строкой: {"kind": "action|question|chat|mission", "tool": "name", "confidence": float}
    │       ├── Уверенное решение ──► Назначенный инструмент / Режим
    │       └── Неуверенность / Двусмысленность ──► Уточнение у пользователя (Clarification)
```

## 3. Ответы на ключевые проектные вопросы

### (1) Порядок прохождения запроса
1. **Точный ключ (Tier-0A)**: Проверяется мгновенно. Срабатывает ТОЛЬКО при полном совпадении с безопасным детерминированным действием (например, «тише», «текущее время»). Несовпадение просто передает управление дальше.
2. **Embedding-скор по Capability Examples (Tier-0B)**: Векторизация фразы через локальный `Embedder` (384-мерный вектор). Сравнение с предрассчитанными векторами возможностей. На этом этапе фразы «врубай телегу» и «почём бакс» уверенно получают скор > 0.8 к `open_app` и `public_data`.
3. **Дешёвая FAST LLM классификация (Tier-1)**: Подключается исключительно в серой зоне (около 15–20% запросов). Модель получает только список из 3–4 наиболее близких кандидатов и выдает структурированный JSON за ~100 мс.
4. **Conversation / Chat**: Если семантический вектор или модель FAST подтверждают отсутствие операционного намерения, запрос передается в свободный диалог.

### (2) Пороги уверенности и поведение в серой зоне
- **High Confidence ($\ge 0.75$)**: Автоматическое исполнение. Приоритет — непрерывность взаимодействия («гладкий ассистент»).
- **Grey Zone ($0.35 \dots 0.75$)**:
  - Если действие **обратимое и безопасное** (LOW risk: чтение погоды, поиск в веб, статус системы, открытие плеера) — система выбирает наиболее вероятный инструмент без лишних переспросов.
  - Если действие **может создать неудобство** (закрытие несохраненного окна, переключение раскладок) — система задает короткий уточняющий вопрос в одно предложение: *«Открыть Telegram или найти информацию о нем?»*
- **Low Confidence ($< 0.35$)**: Запрос направляется по диалоговой ветке.

### (3) Защита High-Risk инструментов
- **Принцип отчужденности Risk Gate**: Оценка риска (`RiskAssessment`) вычисляется **до** и **независимо** от выбора инструмента и уверенности роутера. Высокая уверенность модели не имеет права снижать категорию риска.
- **Двухконтурный контроль**:
  1. *Паспортный риск*: Инструменты удаления файлов, форматирования, завершения процессов, правки реестра/hosts имеют жестко зашитый `risk_level = HIGH / CRITICAL`.
  2. *Семантический вектор опасности*: Расширение проверки риска с плоских regex на векторную близость к деструктивным концептам (удаление, перезапись, завершение сеанса, передача секретов), что ликвидирует 40% слепых зон из текущего baseline.
- **Правило**: Любая команда из зоны High-Risk безусловно блокируется до подтверждения пользователя через UI/голос.

### (4) Полная автономность офлайн
- **Никаких внешних зависимостей для базового цикла**:
  - `all-MiniLM-L6-v2` выполняется локально (ONNX Runtime / SentenceTransformers), потребляет < 80 МБ RAM, отрабатывает за 5–12 мс на CPU.
  - Локальная модель Qwen-4B (тир FAST) развернута через `llama.cpp` / GGUF и используется как для классификации серой зоны, так и для офлайн-диалога.
  - Все базовые системные действия (управление приложениями, окнами, файлами, системным звуком, временем, локальной музыкой) функционируют на 100% без интернета.

### (5) Бюджет латентности маршрутизации
- **Tier-0A (Exact Key)**: $\le 1.0$ мс (встречается в ~30% типовых команд).
- **Tier-0B (Embeddings)**: $8 \dots 15$ мс (для 55% запросов).
- **Tier-1 (Fast LLM в серой зоне)**: $100 \dots 200$ мс (для оставшихся 15% спорных случаев).
- **Интегральный p95**: не более **35–45 мс** для всей массы пользовательских запросов, что укладывается в бюджет реакции реального времени (< 300 мс до начала первого ответа).

### (6) Структурированный Trace (Объяснимость «Почему Jarvis это сделал»)
В объект `AgentOutcome.trace` и журнал сессии пишется стандартизированная запись:
```json
{
  "route_tier": "tier_0b_semantic",
  "top_candidate": "open_app",
  "confidence": 0.84,
  "runner_up": "web_search",
  "runner_up_confidence": 0.31,
  "margin": 0.53,
  "risk_evaluated": "LOW",
  "decision": "fast_path_action",
  "rationale": "High embedding similarity to capability 'open_app' via example 'врубай телегу' ~ 'запусти telegram'"
}
```
Это полностью исключает ситуации, когда невозможно понять, почему запрос ушел в чат или закрыл приложение.

## 4. Слияние и ликвидация избыточных гейтов

Текущая кодовая база перегружена дублирующими и конфликтующими проверками:

### Ликвидируются (Удалить без замены)
1. **Эвристика `intent == 'none' and len <= 8` в `classify_conversation`**: Главный источник деградации продукта, превращающий разговорные команды в бессмысленный smalltalk.
2. **Вторичный `classify_conversation` в `agent.py:982`**: Дублирует проверку, создавая лишние развилки.
3. **Изолированные кортежи фраз в `_try_fresh_information`**: Курсы валют и погода переносятся в паспорта `public_data` и `weather` в `CAPABILITIES`.

### Сливаются в единый конвейер (Unify)
1. **`resolve_keyword_tool` + `CAPABILITIES.retrieve`**: Сливаются в гибридный поисковик `CapabilityRegistry.retrieve()`, где совпадение по тегам дает аддитивный бонус к косинусному расстоянию эмбеддинга, но не является обязательным фильтром.
2. **`UnderstandingLayer` (оркестратор) + `ModelRouter` (агент)**: Устраняется рассинхронизация между оркестратором и ядром агента. Оркестратор использует тот же единый профиль решения, что и агент.
3. **`_extract_simple_args` + семантическое извлечение**: При наличии сильного совпадения инструмента имя приложения или запрос вырезается не только по жестким префиксам `открой `, но и через нормализацию именованных сущностей (словарный lookup установленных приложений).
