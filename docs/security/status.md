## S1 — `assess_risk`: монотонность, границы слов, паспорт как база

**Сделано.** Правки: `core/routing/semantic_router.py` (единый источник оценки),
`core/safety.py` (снят второй экземпляр исключения для снимка экрана).

### Что было сломано (проверено на живой системе до правки)

| Запрос | Было | Стало | Почему было |
|---|---|---|---|
| «включи музыку» | **high** + подтверждение | low | `ключ\w*` без `\b` совпадал внутри «в-**ключи**» |
| «отключи брандмауэр» | **high** | **critical** | секция 5 (секреты, `от-ключи`) присваивала `level = "high"` ПОВЕРХ critical секции 4 |
| «удали файл hosts» | high | critical | то же понижение; удаление оценивалось **ниже** чтения |
| «покажи файл hosts» | critical | critical | — |
| «сделай скриншот» / `screen_capture` | **low** | medium (паспорт) | явное исключение отключало паспортный риск в двух файлах |

Три дефекта, все в одну сторону — **ложное разрешение**:

1. Секции 1–6 присваивали уровень напрямую (`level = "high"`), поэтому позднее
   правило понижало вердикт раннего.
2. Цепочка `elif` в секции массовых операций гасила ветки с более высоким
   уровнем (совпадение массовости на high пропускало форматирование на critical).
3. Регулярки без границ `\b` совпадали внутри слов.

Цена дефекта не косметическая: `core/authority.py` сравнивает `request.risk` с
`grant.risk_ceiling`, и совпавший грант возвращает `needs_confirmation=False`.
Понижение critical→high означает, что грант с `ceiling=high` молча авторизует
критическое действие.

### Как устроено теперь

* **База — паспорт возможности** (`core/capabilities.py: risk_level`), с
  per-action динамикой (`browser_bridge` навигация/чтение → low, `computer_mouse:move`,
  `computer_keyboard:focus_window` → low). Это единственное место, где уровень
  *задаётся*. Снимок экрана из списка исключений **убран** (S1d) — в обоих файлах.
* **Текст и аргументы только повышают** уровень через `max_level`. Правила стали
  независимыми `if` вместо цепочки `elif`.
* `Capability` **не имеет поля `effect`** (проверено на диске): эффект
  классифицирует `core/authority.classify_effect` по тексту запроса, а
  `permissions` — описательные метаданные и уровень не задают. Поэтому «база из
  метаданных» = `risk_level` + per-action динамика, без `effect`/`permissions`.

### S1(g) — ответ: дыры в fast path НЕТ

Из двух вариантов верен **второй**: `_try_fast_path` не обходит
`requires_confirmation`. Гейт стоит **дважды**:

* [`core/agent.py:1802`](../../core/agent.py) — `if risk.needs_confirmation or decision is None: return None`;
* [`core/agent.py:1825-1827`](../../core/agent.py) — `exec_risk = assess_risk(goal, cap.name, args)` пересчитывается
  на **извлечённых аргументах**, и при `needs_confirmation` тоже `return None`.

Почему «включи музыку» вообще попала в вопрос: в `tests/test_media_fast_path.py`
используется фраза «**поставь** музыку», в которой нет `ключ`. Настоящая фраза
«включи музыку» была **заблокирована** ложным HIGH — то есть это был дефект
удобства (false positive), а не обход подтверждения. Свойство всё равно
закреплено тестом: при `needs_confirmation=True` инструмент не исполняется, плюс
контрольный прогон доказывает, что останавливает именно гейт риска, а не другой
фильтр fast path.

## Протокол прогонов (действует для всех пунктов)

`pytest` зависает **после** печати итоговой строки, на завершении процесса.
Замерено отдельно по каталогам:

| Набор | Тесты | Итог | Завершение процесса |
|---|---|---|---|
| `tests/regressions` | 103 (76 на момент S0) | все зелёные | сам, код 0 |
| `tests/routing` | 42 | `42 passed … in 21.64s` (S0) / `39.65s` (S1) | **зависает**, убит по таймауту |

То есть зависание локализовано в `tests/routing`: тесты проходят за 21 с, после
чего процесс не выходит. Это отдельная проблема (не-daemon поток или незакрытый
loop), её чинит следующая задача — здесь она только зафиксирована.

Следствие для проверок: строка `N passed` печатается **до** зависания, поэтому
результат читается из лога, а код выхода 124 (убит по таймауту) не считается
падением тестов. Запуск: `timeout -k 5 <N> python -u -m pytest <paths> > log`,
без дополнительного `-q` (в `pyproject.toml` `addopts = "-q"` уже есть; второй
`-q` подавляет итоговую строку — на этом можно ошибочно принять зелёный прогон
за пустой).
